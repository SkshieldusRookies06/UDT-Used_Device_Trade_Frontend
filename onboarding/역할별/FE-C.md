## 5. 내 티켓 — 하나씩 어떻게 하나

> 아래는 **티켓을 실제로 어떻게 하는가**다. 순서대로 하면 된다.
> **백엔드를 기다리지 않는다** — `npm run mock` 이면 계약대로 응답이 온다.

### T-016 — 마이페이지 4탭 (D1~D3)

`pages/MyPage/` 가 골격만 있다. **탭 4개 = 목록 4개**다 — 같은 구조를 네 번 쓴다.

**1) 먼저 `pages/ProductListPage/` 를 읽는다 (30분) ← 첫 단계다**
팀의 기준 구현이다. **네 상태를 어떻게 나눠 그리는지**와 **URL을 어떻게 정본으로 쓰는지**가 거기 있다.
내 화면도 같은 구조를 따른다.

**2) 탭 상태를 URL에 둔다 — `useState`로만 두지 않는다**

```js
const [params, setParams] = useSearchParams();
const tab = params.get("tab") ?? "products";  // products | selling | buying | wishes  ← T-016 수용 기준의 값
```
> 새로고침해도 탭이 유지되고, "내 거래 탭 링크"를 보낼 수 있다. 규약 F2다.

**3) 탭 4개를 각각 만든다**

| 탭 | 엔드포인트 | 재사용할 것 |
|---|---|---|
| 내 상품 (`?tab=products`) | `GET /api/me/products` |
| 판매 내역 (`?tab=selling`) | `GET /api/me/transactions?role=seller` | **`ProductCard`** + `StatusBadge`(검수대기/판매중/거래중/거래완료) |
| 구매 내역 (`?tab=buying`) | `GET /api/me/transactions?role=buyer` | `StatusBadge` — 누르면 `/transactions/:id` 로 |
| 찜 목록 (`?tab=wishes`) | `GET /api/me/wishes` | **`ProductCard`** |

> **비슷한 카드를 새로 만들지 않는다.** `ProductCard`·`StatusBadge`가 이미 있다.
> 부족하면 FE-A에게 **요청**한다 (`components/`는 FE-A 소유).

**4) 탭마다 네 상태를 다 만든다**
특히 **빈 결과**: "아직 등록한 상품이 없습니다" — **에러 화면이 뜨면 틀렸다.**
빈 목록은 정상 상태다. 신규 사용자는 세 탭이 모두 비어 있다.

**5) 확인한다**

```bash
grep -rn "axios" src/pages/MyPage     # 무출력
npm run build                          # 에러 0
```

`확인:` 탭을 바꾸면 URL이 바뀌고, 새로고침해도 그 탭이 유지된다 · 빈 탭이 에러가 아니다.

### T-017 — 거래 상세 · 상태별 액션 · 분쟁 신고 (D3~D5 · ★ 서비스의 중심 화면)

**0) BE-D에게 표를 먼저 받는다 ← 이게 없으면 시작할 수 없다**

| Transaction 상태 | 구매자 | 판매자 |
|---|---|---|
| `PAID` | 분쟁 신고 | 송장 입력 |
| `SHIPPING` | **구매확정** · 분쟁 신고 | — |
| `DISPUTED` | — | — (관리자만) |
| `CONFIRMED` · `REFUNDED` | — | — |

> D1 회의에서 받는다. 받기 전까지는 T-016을 한다.

**1) 상태 판정을 화면에 흩지 않는다 — 이 화면의 핵심 설계다**

나쁜 예 (조건이 늘어나면 손댈 수 없어진다):
```
{txn.status === "SHIPPING" && me.id === txn.buyerId && <button>구매확정</button>}
{txn.status === "PAID" && me.id === txn.sellerId && <button>송장</button>}
...
```

좋은 예 — **한 곳에 모은다**:
```js
// pages/TransactionDetailPage/actions.js
export const isBuyer  = (t, me) => t.buyerId === me.id;
export const isSeller = (t, me) => t.sellerId === me.id;

export const canConfirm           = (t, me) => isBuyer(t, me)  && t.status === "SHIPPING";
export const canRegisterShipping  = (t, me) => isSeller(t, me) && t.status === "PAID";
export const canOpenDispute       = (t, me) => isBuyer(t, me)  && ["PAID", "SHIPPING"].includes(t.status);
```
> **표가 바뀌면 이 파일 하나만 고친다.** JSX는 `canConfirm(txn, me) && <Button/>` 만 쓴다.

**2) 상태 × 역할을 **둘 다** 본다**
상태만 보면 구매자에게 판매자 버튼이 보인다. 이게 이 화면에서 가장 흔한 버그다.

**3) 액션 3개를 붙인다**

```
구매확정   PATCH /api/transactions/{id}/confirm
           → 되돌릴 수 없다. 확인 모달을 띄운다
           → 성공하면 응답의 새 상태로 화면을 다시 그린다
송장 입력  PATCH /api/transactions/{id}/shipping  { courier, trackingNo }
분쟁 신고  POST  /api/transactions/{id}/disputes  (multipart: 사유 + 증빙 파일)
```
> **성공 응답을 화면에 반영한다.** 서버가 새 상태를 돌려주니 그걸로 다시 그린다.
> 낙관적으로 미리 바꾸지 않는다 — 상태 전이는 서버가 거절할 수 있다.

**4) 분쟁 신고 폼**

```
1) 사유 (필수)
2) 증빙 파일 여러 개 — URL.createObjectURL 로 미리보기, 해제도 잊지 않는다
3) multipart 로 전송
4) 성공하면 상태가 DISPUTED 로 바뀌고 모든 액션 버튼이 사라진다
```

**5) 잔액을 화면에 보이게 배치한다 ← 발표를 위한 설계다**
구매확정 버튼 근처에 **구매자 잔액 · 판매자 잔액 · 거래 금액**이 같이 보이게 둔다.
발표 ⑦에서 "구매확정을 누르는 순간 판매자 잔액이 늘어난다"를 화면 하나로 보여 줄 수 있다.
**이게 이 서비스의 존재 이유를 증명하는 장면이다.**

**6) 상태 5종을 눈으로 다 본다**
시드에 거래가 **4건**(PAID·SHIPPING·CONFIRMED·DISPUTED) 있다 — `/transactions/1` ~ `/transactions/4`. 계정 2개로 번갈아 들어가 상태를 진행시키며 확인한다.

```
buyer1@udt.test / seller1@udt.test   (둘 다 Test1234!)
브라우저 창 2개(일반 + 시크릿)를 띄워 두면 전환이 빠르다
```

**7) 확인한다**

```bash
grep -rn "axios" src/pages/TransactionDetailPage   # 무출력
npm run build                                       # 에러 0
```

`확인:` 거래 상태 5종 × 역할 2종에서 버튼이 정확히 맞는다 · 분쟁 신고 후 액션이 전부 사라진다 ·
구매확정 시 판매자 잔액이 화면에서 늘어난다.

## 10. 발표에서 내가 말하는 것

**시연 ④⑤⑦ 구간 조작 (발표 3분 중 하이라이트)** — 슬라이드 발표는 없지만 **마우스를 내가 잡는다**

```
④ 판매자 → 송장번호 입력 → "배송중"
⑤ 구매자 → 분쟁 신고(증빙 사진 첨부) → "분쟁"
⑦ (정상 경로) 구매확정 → 판매자 잔액 증가 · 상품 "거래완료"
```

> **⑦이 이 서비스의 존재 이유다.** 구매확정 전까지 대금이 판매자에게 가지 않는다는 걸
> 잔액 숫자로 보여 주는 순간이 발표의 정점이다. 잔액이 화면에 보이게 미리 배치해 둔다.

> **경로를 외운다.** 계정 2개를 오가야 해서 가장 헷갈리는 구간이다 —
> 브라우저 창 2개(일반 + 시크릿)를 미리 띄워 두면 전환이 빨라진다.
> 영상 백업을 먼저 찍어 둔다.

마무리 1분에 **한 줄씩** 말한다 (`retro-<이름>.md` 5번에서 가져온다).

```
4. 계약에 대한 구두 합의는 SPEC.md에 커밋되기 전까지 무효
```

에이전트에 맡길 때는 **지시서(`tasks/T-###.md`) + SPEC 해당 절 + (수정이면) diff** 셋만 넣는다.
리포를 통째로 넣지 않는다. 커밋·push·머지는 사람이 한다.
