## 5. 내 티켓 — 하나씩 어떻게 하나

### T-013 — 상품 목록 마감 (D1~D2)

`pages/ProductListPage/` 는 **이미 거의 다 돼 있다.** 네 상태·검색·페이징이 들어 있는
**팀의 기준 구현**이다. 내 일은 **읽고 → 카테고리 필터를 더하는 것**이다.

**1) 먼저 기존 코드를 읽는다 (30분) ← 이게 첫 단계다**

| 볼 것 | 확인할 것 |
|---|---|
| `index.jsx` | 네 상태(로딩·정상·빈 결과·에러)를 **어떻게 나눠 그리는지** |
| | 검색어·페이지를 `useSearchParams`로 읽는지 — **URL이 정본이다** |
| `Pagination.jsx` | 0-base 페이지를 어떻게 다루는지 |
| `../../api/products.js` | 내 파일이다. 함수 추가는 내가 한다 |
| `../../api/client.js` | **읽기만 한다.** 봉투는 인터셉터가 이미 벗겼다 — 화면은 알맹이만 본다 |

> 여기서 **네 상태를 어떻게 나눴는지**를 이해하면 T-014·T-015가 절반은 끝난다.

**2) 카테고리 목록을 불러온다**

`api/products.js`에 **이미 있다** — 새로 추가하면 `Duplicate export` 로 빌드가 깨진다.

```js
// src/api/products.js (내 파일) — 이미 존재하는 줄
export const fetchCategories = () => client.get("/api/categories");
```
화면에서 import 해서 쓰기만 한다.

**3) 필터 UI를 붙인다 — 상태를 `useState`에 넣지 않는다**

```js
const [params, setParams] = useSearchParams();
const categoryId = params.get("categoryId") ?? "";
// 바꿀 때: setParams({ q, categoryId, page: 0 })  ← 필터가 바뀌면 page 를 0으로
```
> **왜 URL인가**: 새로고침해도 유지되고, 뒤로가기가 맞게 돌고, 링크를 공유할 수 있다.
> `useState`에 넣으면 셋 다 깨진다. 발표에서 나오는 질문이기도 하다.

**4) 네 상태를 직접 눈으로 본다**

| 상태 | 만드는 법 |
|---|---|
| 정상 | `/?page=0` |
| **빈 결과** | `/?q=__none__` → **"조건에 맞는 상품이 없습니다"**(SPEC §3.3 계약 문구) · **에러 화면이 뜨면 틀렸다** |
| 에러 | 목 서버를 끄고 새로고침 → 에러 + 다시 시도 버튼 |
| 로딩 | 개발자도구 Network를 Slow 3G로 |

**5) 규약을 확인한다**

```bash
grep -rn "axios" src/pages/ProductListPage        # 무출력
grep -rnE "#[0-9a-fA-F]{3,6}" src/pages/ProductListPage/*.module.css   # 무출력
npm run build                                      # 에러 0
```

`확인:` 네 상태가 눈으로 확인됨 · 새로고침해도 검색어·카테고리·페이지가 살아 있음.

### T-014 — 상품 상세·찜·구매 (D2~D3)

**1) `ProductDetailPage`의 네 상태부터 만든다** — 목록에서 본 구조 그대로

특히 **404**: 없는 상품 id로 들어오면 에러 화면에 "존재하지 않는 상품입니다"를 띄운다.
서버가 `PRODUCT_NOT_FOUND` 와 함께 `message`를 준다. **문구를 새로 쓰지 않는다.**

**2) 이미지 갤러리**
`images[]`가 비어 있을 수 있고 `thumbnailUrl`이 `null`일 수 있다. **null이 정상 값이다** —
키가 없는 게 아니라 값이 null이니, 있으면 쓰고 없으면 자리표시자를 그린다.

**3) 찜 토글 — 낙관적 UI**

```
1) 누르는 즉시 하트를 바꾼다 (서버 응답을 기다리지 않는다)
2) 요청을 보낸다
3) 실패하면 되돌린다
```
> 서버에 `(userId, productId)` unique 제약이 있어서 따닥 눌러도 두 줄이 안 생긴다. 그걸 믿고 만든다.
> `wishStore`는 FE-A 소유다. 고쳐야 하면 **요청**한다.

**4) 구매 버튼 — 여기가 이 티켓의 함정이다**

```
1) 비로그인이면 /login 으로 (돌아올 곳을 기억시킨다)
2) 본인 상품이면 버튼을 아예 숨긴다
3) status !== "ON_SALE" 이면 비활성 + 이유 표시
4) 누르면 즉시 disabled  ← 중복 구매 요청이 나가는 걸 막는다
5) 성공하면 거래 상세로 이동
6) 실패는 code 로 분기:
   INSUFFICIENT_BALANCE      → "잔액이 부족합니다"
   PRODUCT_NOT_ON_SALE       → 서버 message("판매 중인 상품이 아닙니다") 그대로 + 새로고침 버튼
   SELF_PURCHASE_NOT_ALLOWED → 버튼이 보이면 안 되는 상황
```
> **4번을 빼먹으면 D8 시연에서 거래가 두 개 생긴다.** 서버가 막아 주긴 하지만 화면이 이상해진다.

`확인:` 찜 두 번 눌러도 상태가 일관됨 · 구매 버튼이 요청 중 눌리지 않음 · 세 에러가 각각 다른 문구.

### T-015 — 상품 등록·이미지 미리보기 (D5~D6)

**1) 폼을 만든다** — 제목 · 설명 · 가격 · 상태등급 · 카테고리 · 이미지

**2) 이미지 미리보기**

```js
const url = URL.createObjectURL(file);      // <img src={url} />
// 컴포넌트가 사라질 때 URL.revokeObjectURL(url)  ← 안 하면 메모리가 샌다
```

**3) 전송은 multipart 그대로** — **base64로 바꾸지 않는다**

```js
const fd = new FormData();
fd.append("product", new Blob([JSON.stringify(body)], { type: "application/json" }));
files.forEach((f) => fd.append("images", f));
```
> `product` 파트에 `type: "application/json"` 을 꼭 준다. 없으면 서버가 JSON으로 안 읽는다.

**4) 프론트 검증은 편의일 뿐이다**
확장자·용량을 미리 걸러서 왕복을 줄이되, **서버 검증이 진짜 방어선**이다.
서버가 거절하면 그 `message`를 띄운다.

**5) 등록 성공 후 안내가 중요하다**
등록한 상품은 **`INSPECTING`(검수대기)** 이지 판매중이 아니다.
"관리자 검수 후 판매중으로 전환됩니다"를 보여 준다. **이게 이 서비스의 특징이고 시연 ①이다.**

**6) `createProduct` 시그니처를 바꿀 거면 T-013·T-014를 같이 고친다** — 세 화면이 같은 `api/products.js`를 쓴다.

`확인:` 사진 3장 미리보기 → 등록 → `INSPECTING` 안내 → 목록에는 아직 안 보임(정상).

## 12. 내가 지키는 네 줄

```
1. SPEC.md에 답이 없으면 추측하지 않는다 — 멈추고 오너에게 묻는다
2. "됐습니다"는 증거가 아니다 — 게이트 출력이 증거다
3. 위 2번 밖의 파일은 틀려 보여도 고치지 않는다 — 오너에게 보고
4. 계약에 대한 구두 합의는 SPEC.md에 커밋되기 전까지 무효
```

에이전트에 맡길 때는 **지시서(`tasks/T-###.md`) + SPEC 해당 절 + (수정이면) diff** 셋만 넣는다.
리포를 통째로 넣지 않는다. 커밋·push·머지는 사람이 한다.
